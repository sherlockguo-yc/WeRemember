# WeRemember V1 需求基线

> 状态：待确认（2026-11-11）

## 1. 用户场景

我（及家人）买回护肤品、食品、电子产品后，包装盒很快会丢。我希望在拿到物品的当下录一次，之后系统在合适的时间主动提醒我"该优先用了 / 快过期了 / 已过期该丢了"；同时能把电子产品说明书存起来，忘了怎么操作时随时查，不用问客服。

## 2. 范围

### V1 做
- 手机端 PWA（添加到主屏幕），技术栈参照 WeHousework：Node + Express + SQLite（better-sqlite3）+ Vite，部署到 N150。
- 两个独立模块，底部两个 Tab：「保质期」「说明书」。数据结构、页面互相独立。
- 多用户账号 + 家庭组共享。邀请码注册。
- 提醒渠道：App 内列表、Server酱（微信）、QQ 邮件。

### V1 不做（记录备查）
| 项 | 说明 | 何时做 |
|----|------|--------|
| PWA Web Push | 需要 VAPID + Service Worker + 订阅管理，iOS 有版本门槛 | V1.1 |
| 拍照 OCR 识别日期 | V1 只预留照片字段与入口 | V2 |
| 开封后有效期（PAO） | 见 5.4 | 有需要时 |
| 企业微信群机器人 | 普通用户多半没有企业微信，Server酱即可 | 不做 |
| 说明书全文搜索 | V1 只按名称/分类/备注搜索 | 暂无计划 |

## 3. 数据流

### 3.1 账号与家庭组
- 注册：用户名 + 密码 + 注册邀请码。注册邀请码一次性使用，7 天有效，由管理员在设置页生成。
- 首个管理员：服务启动时读取环境变量 `ADMIN_INVITE_CODE`，该码只能用一次，用它注册的用户成为管理员。之后该变量失效。
- 注册成功自动创建一个「个人空间」（家庭组，仅自己）。用户可再创建家庭组，或用「家庭组邀请码」加入他人的家庭组。家庭组邀请码与注册邀请码是两回事：前者让已有账号加入某个组，后者允许创建账号。
- 用户可属于多个组。物品、说明书都归属某一个组，组内所有成员可见、可编辑、可标记处理。
- 首页顶部有组筛选，默认「全部」，聚合所有所属组的数据。

### 3.2 保质期物品
录入字段：
| 字段 | 必填 | 说明 |
|------|------|------|
| 名称 | 是 | 最长 50 字 |
| 分类 | 是 | 护肤品 / 食品 |
| 所属组 | 是 | 默认个人空间 |
| 生产日期 | 否 | |
| 保质期时长 | 否 | 数值 + 单位（天/月/年），与生产日期配合算到期日 |
| 到期日期 | 否 | 可直接填；与「生产日期 + 保质期」二选一 |
| 备注 | 否 | 最长 200 字，如存放位置"冰箱二层" |
| 包装日期照片 | 否 | 预留 OCR；V1 只存图，不识别 |

规则：
- 到期日 = 直接填写的到期日期；否则 = 生产日期 + 保质期。两种都不满足 → 到期日为空（见 6）。
- 所有日期按北京时间的日期（YYYY-MM-DD）处理，不带时分秒。
- 提醒计算的起点（`base_date`）：有生产日期取生产日期，否则取录入日期。总保质期 = 到期日 − `base_date`。

### 3.3 提醒计算（分阶段）
固定天数对长保质期没用（3 年的护肤品提前 14 天已经不敢用），所以按「剩余时间占总保质期的比例」设提醒点。

| 分类 | 提醒点（剩余占总保质期） | 另加 |
|------|--------------------------|------|
| 食品 | 50% / 25% / 10% / 3% | 到期当天 |
| 护肤品 | 35% / 15% / 5% | 到期当天 |

- 提醒点距到期天数 = `ceil(总保质期 × 比例)`，最少 1 天。去重后相同天数只保留一个。大于总保质期的点丢弃。
- 过期后：每 3 天提醒一次，直到用户标记处理。
- 举例（食品 1 年 = 365 天）：到期前 183 天、92 天、37 天、11 天、到期当天。
- 举例（护肤品 3 年 = 1095 天）：到期前 384 天、165 天、55 天、到期当天。
- 举例（食品 3 个月 = 90 天）：到期前 45 天、23 天、9 天、3 天、到期当天。
- 每个提醒点带语义：
  - 第一个提醒点：「开始留意，规划使用」
  - 中间的提醒点：「该优先使用了」
  - 最后一个提醒点：「马上过期，尽快用掉」
  - 到期当天：「今天到期，请不要再使用」
  - 过期后：「已过期，请丢弃，避免误用」
- 补录不轰炸：录入时若已经越过若干提醒点，只发当前所处阶段的那一次，不补发之前错过的。
- 去重：每个物品记录 `last_stage`（已发到第几阶段）；阶段只会前进，不会回退。
- 到期日被用户修改后，`last_stage` 按新日期重新判定（不重复发已越过的阶段）。

### 3.4 提醒发送
- 每日定时任务，默认北京时间 9:00，每个用户可在设置里改发送时刻（整点）。
- 每个用户每个渠道每天最多一条汇总消息，列出该用户所属各组当天触发提醒的全部物品（含名称、所属组、剩余天数、语义文案）。当天没有触发项则不发。
- 渠道：
  - **Server酱**：用户在设置里填 SendKey，开关 + 「发送测试消息」按钮。后端 POST `https://sctapi.ftqq.com/<SendKey>.send`（实现时先用真实 Key 调通再写入代码）。
  - **QQ 邮件**：发件人为系统统一的 QQ 邮箱，授权码放服务器环境变量，不入库；用户在个人信息里填收件邮箱，开关 + 「发送测试邮件」按钮。设置页提示「请把发件地址加入白名单，避免进垃圾箱」。
  - **App 内**：首页「待处理」区，永远可用，不依赖任何渠道。
- 各渠道独立发送，一个渠道失败不影响其他；失败记入发送日志，不重试当天已成功的渠道。

### 3.5 说明书库
- 上传文件（PDF / 图片：jpg/png/webp）+ 产品名称（必填）+ 分类（自由输入，常用项可选）+ 备注（选填）+ 所属组。
- 文件存 `data/manuals/<组ID>/`，不走静态目录；下载与预览接口校验登录与组成员身份。
- 元信息存库。列表支持按产品名 / 分类 / 备注关键词搜索。
- PDF 用浏览器内嵌预览，图片直接展示，均可下载。
- 单文件上限 20MB，超出拒绝并提示。

## 4. 状态机

### 4.1 物品状态
```
录入 ──> 正常（距第一个提醒点还早）
正常 ──> 留意（越过第一个提醒点）
留意 ──> 优先使用（越过中间提醒点，可有多个）
优先使用 ──> 临期（越过最后一个提醒点）
临期 ──> 已过期（超过到期日）
任意状态 ──> 已处理（用户点「已用完」或「已丢弃」）
已处理 ──> 恢复（误点时可撤销，回到按日期计算的状态）
```
- 到期日为空的物品：状态为「未设置到期日」，不参与提醒。
- 「已处理」为终态：停止提醒、移入历史，数据不删除。
- App 内标签：正常无标签；留意（淡黄）；优先使用（橙）；临期（红橙）；已过期（红）。
- 并发：两个组员同时点「已处理」，后一次为幂等操作，不报错。快速双击按钮时，请求中禁用按钮。

### 4.2 页面状态
- 列表：加载中 / 空（引导录入第一个物品）/ 正常 / 加载失败（重试按钮）。
- 渠道设置：未配置 / 已配置未验证 / 测试成功 / 测试失败（显示失败原因）。

## 5. 设计决策与取舍

### 5.1 为什么两个独立模块
保质期提醒围绕「日期 + 状态机 + 定时任务」，说明书库围绕「文件 + 搜索」，字段、页面、后台逻辑几乎没有交集。合并成统一台账只会让字段变成大量可空列。两者仅共用账号、家庭组和部署。

### 5.2 为什么按比例而不是固定天数
固定「3 天 / 14 天」对 1 年以上的保质期来说为时已晚。比例法让短保质期（3 个月）和长保质期（3 年）都自动得到合适的提前量，且无需用户手动设置。

### 5.3 为什么渠道分阶段
Server酱和邮件只需一个 HTTP 请求 / SMTP 调用；PWA Web Push 要 VAPID 密钥 + Service Worker + 订阅管理，且 iOS 需添加到主屏幕。先做前两者，核心提醒能力当天可验证。

### 5.4 开封后有效期（PAO）——V1 不做，备查
护肤品开封后通常只能用 6–12 个月，比包装到期日短。未来如需要，增加两个可选字段「开封日期」「开封后可用月数」，有效到期日取「包装到期日」与「开封日 + 可用月数」中较早者，其余提醒逻辑不变。V1 不纳入的原因：开封后有效期短的物品用得快，不容易忘。

### 5.5 为什么邀请码注册
邮件由系统 QQ 邮箱代发，开放注册会让任何人借其向任意地址发邮件；说明书上传会被刷满磁盘。

## 6. 边界与失败

| 情况 | 处理 |
|------|------|
| 没有生产日期，也没有到期日 | 允许保存，状态为「未设置到期日」，不提醒，列表置底并提示补录 |
| 只有到期日、无生产日期 | `base_date` 取录入日期；总保质期偏短，提醒点相应偏晚，录入页提示"填写生产日期提醒会更准" |
| 到期日早于生产日期 | 前端校验拒绝 |
| 保质期时长为 0 或负数 | 前端与后端都拒绝 |
| 录入时已过期 | 允许保存，直接按「已过期」处理，下次定时任务发一次 |
| 用户没配任何渠道 | 系统正常工作，只剩 App 内列表 |
| Server酱 / QQ 邮箱发送失败 | 记入发送日志，设置页显示最近一次失败原因；不影响其他渠道 |
| 服务停机错过 9:00 | 服务恢复后，定时任务补跑当天未发送的汇总（按 `用户 + 日期 + 渠道` 发送记录去重） |
| 用户把家庭组里的物品被他人标记已处理 | 所有成员的待处理区同步消失，提醒停止 |
| 退出家庭组 | 不再收到该组的提醒，也看不到该组数据；该组数据保留给其他成员 |
| 说明书文件超过 20MB / 类型不支持 | 拒绝并提示具体原因 |
| 邀请码过期 / 已使用 / 不存在 | 注册失败，提示具体原因 |
| 注册邀请码和登录接口被暴力尝试 | 对登录与注册接口做按 IP 限流 |

## 7. 影响面
全新项目，不影响已有项目。复用 WeHousework 的技术栈与家庭组模式（实现时参考其 `server/routes/groups.js`），但不改动 WeHousework 任何代码。后续部署接入 N150 的 deploy-agent 体系时，需在 `~/.deploy-projects.conf` 增加一行，并在 WeMonitor 中会自动补全健康检查。

## 8. 验收标准
1. 管理员用 `ADMIN_INVITE_CODE` 注册，在设置页生成一个注册邀请码；另一个新用户用该码注册成功，同一个码再用一次被拒绝。
2. 录入一个 1 年保质期的食品：按剩余天数排序，到期日前 183 / 92 / 37 / 11 天和到期当天分别触发提醒阶段；录入一个已越过两个提醒点的物品，只收到当前阶段的一次提醒。
3. 在设置里填好 Server酱 SendKey 和收件邮箱并点「发送测试」，微信和邮箱各收到一条测试消息；到发送时刻，当天有触发提醒的物品，微信和邮箱各收到一条汇总消息，且内容含物品名、所属组、剩余天数。
4. 家庭组：A 创建家庭组并把邀请码给 B，B 加入后能看到 A 录入的物品；B 点「已丢弃」后，A 的待处理区也消失，A 不再收到该物品的提醒。
5. 说明书：上传一个 PDF 和一张图片，用产品名关键词搜索可找到，点开能预览；上传 25MB 的文件被拒绝并有明确提示。
6. 在没有配置任何推送渠道的情况下，首页「待处理」区仍然能看到临期和过期的物品。
